Model + hardware guide

Understand why a model fits, loads, and runs.

Beginner guide
01

The model is a file of weights

Parameters are the learned numbers. At full precision, model storage is roughly parameters × bytes per weight. A 7B FP16 model is therefore much larger than 7B at 4-bit.

How model weights load ↗
02

Quantization trades precision for fit

Quantization stores weights at fewer bits. It reduces file size and bytes read per token, but lower precision can reduce task quality. K-quants protect more sensitive tensor groups; the effective bits per weight are not always the label.

Hugging Face quantization overview ↗
03

Context needs extra memory

The KV cache stores key/value states from prior tokens. It grows with context, attention layers, KV heads, head dimension, users and KV precision. Weight memory alone is not the complete fit test.

KV cache strategies ↗
04

Memory capacity determines loading

Weights, quantization metadata, KV cache, temporary buffers and runtime overhead must fit usable VRAM/RAM. CPU offload can rescue fit, but PCIe transfers and system-memory bandwidth usually reduce speed.

GPU inference memory guide ↗
05

Bandwidth drives decode speed

After the prompt is processed, each generated token usually rereads the active weight data. A useful planning approximation is runtime efficiency × available bandwidth ÷ bytes read per token.

decode tok/s ≈ efficiency × GB/s ÷ active GB/token

06

Prefill is different from decode

Prefill processes the prompt in parallel and is often compute-heavy. Decode generates one token at a time and is often memory-bandwidth-heavy. A machine can therefore have fast prefill and slow decode, or the reverse.

07

Dense and MoE models use compute differently

A dense model activates all its parameters. A mixture-of-experts model activates only selected experts per token, so total storage can be large while active compute is much smaller.

08

The runtime must understand the model and chip

Model architecture, tensor format, quantization format, attention kernels and accelerator backend must be supported by llama.cpp, vLLM, SGLang, OpenVINO, MLX, or another runtime.

llama.cpp feature matrix ↗
09

Unified memory is shared, not infinite

Unified-memory systems share one pool among CPU, GPU and runtime. The operating system, display, other applications and GPU allocation leave less than the physical total available to the model.

10

Measured and estimated are not the same

Estimated speed is a planning model. A measured result must name its machine, model artifact, revision, runtime/build, quantization, context, workload, repetitions and source.

Glossary

Terms used by the selector.

Parameter
One learned weight in the model.
Total parameters
All checkpoint parameters, including experts that may not run for every token.
Active parameters
Parameters used for one token; especially important for MoE models.
Quantization
Representing weights or cache values with fewer bits to reduce memory and bandwidth.
Bits per weight
Average storage per parameter, including quantization overhead.
Context
Maximum prompt plus generated-token sequence the model can attend to.
KV cache
Stored key/value vectors reused during token generation.
KV heads / head dimension
Attention geometry that determines how much cache each token and layer stores.
Prefill
The first pass that processes the input prompt.
Decode
Generating output tokens one step at a time after prefill.
Bandwidth
How quickly memory can feed bytes to the processor; often the decode bottleneck.
VRAM / RAM
Accelerator-local memory versus host system memory; offload moves work or data between them.
CPU offload
Running some model layers or cache on system RAM when GPU VRAM is insufficient.
GGUF
A portable model file format commonly used by llama.cpp-compatible runtimes.
Runtime
The inference engine that loads, quantizes and executes model tensors on selected hardware.
OOM
Out of memory: capacity is insufficient for the selected model, context, cache and runtime buffers.
Tok/s
Generated tokens per second; always verify whether a source reports prefill, decode or end-to-end speed.

01

Weights

total params × bits per weight / 8 × 1.03

Total checkpoint payload plus a 3% file margin.

02

KV cache + overhead

2 × layers × KV heads × head dim × KV bits / 8 × context × users

KV cache at 4, 8 or 16 bits, plus 7% of the weights for execution overhead.

03

Decode

runtime efficiency × bandwidth / (active params × bits / 8) / users

Efficiency comes from the runtime table for the hardware class. Each extra identical card adds 80% of its bandwidth.

04

CPU offload

1 / (bytes per token × (GPU share / GPU rate + CPU share / CPU rate))

When a model spills past GPU memory, the overflow runs from host RAM (installed RAM minus 8 GB) at CPU speed. Only llama.cpp, Ollama, LM Studio and IPEX-LLM split a model this way.
